先约定含义，
再选择表情。

以 emoji 作为表达入口，以稳定的 key 连接不同的表情图片。

01　工作约定

AI 输出规范 Unicode 表情；应用将它映射到语义 key，再从当前表情包取出对应图片。表情包更换画风，不更改 key 的含义或 Unicode 映射。 

😭 → crying → 当前表情包中的大哭图片
当前实现与兼容性

本页按 dsh-emoji 的当前代码整理。它接受的语义集标识是 dsh-emoji-core@1。历史设计中的 uniemoji-core@1 不是该实现支持的上传包标识，请勿混用。未来实现的包格式与能力以各自文档为准。

02　40 种语义映射

每个规范 emoji 唯一对应一个 key。另接受 😄 → laughing、🙂 → happy 两个输入别名；其他 emoji 保持原样，不根据上下文猜测，也不自动补图。

03　dsh-emoji 表情包格式

这是当前实现的导入格式。ZIP 内直接放置以下文件，或在外面包一层目录。每个标准 key 必须且只能提供一张同名 PNG，共 40 张。 

my-pack.zip
├── pack.json
└── images/
    ├── happy.png
    ├── crying.png
    └── ...其余 38 个 key.png
{
  "schemaVersion": 1,
  "keySet": "dsh-emoji-core@1",
  "id": "my-pack",
  "name": "我的表情包",
  "version": "1.0.0"
}

schemaVersion 标识文件格式，keySet 标识语义集合。id 使用小写字母、数字与连字符，版本遵循 SemVer。同一个 id 与版本的素材不可覆盖，更新图片须提升版本。

dsh-emoji 限制 ZIP 不超过 20 MiB、解压后不超过 80 MiB、单文件不超过 2 MiB，图片宽高不超过 512 像素。更多命名校验及上传步骤见 实现文档 ↗。

素材库 ≠ 可导入的表情包

素材库 按平台收录原始表达，尚未逐套完成 40 个 key 的标准映射。AVIF 素材不能直接当作上述 PNG 包导入。制作或分发表情包时还需确认素材使用权限。

04　接入与边界

应用负责识别规范 emoji、选择表情包并展示图片。建议保留原始 emoji 作为替代文本，让图片加载失败时仍能传达含义。

dsh-emoji 会保护代码、链接及普通 Markdown 图片，不将它们当作待替换的表情。不同应用需要根据自身的文本格式、流式输出和消息存储方式实现转换，不能仅对整段 Markdown 做无差别替换。

想体验已有实现？前往 dsh-emoji。也欢迎为其他应用开发实现。
